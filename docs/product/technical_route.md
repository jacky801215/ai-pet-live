# AI Pet Live 技术路线

**版本**: v0.1  
**日期**: 2026-09-19  
**作者**: Q仔  
**定位**: AI互动宠物直播引擎

---

## 路线总览

```
第一阶段              第二阶段              第三阶段
验证互动玩法    →    验证直播接入    →    商业化复制
（能不能互动）        （能不能上播）        （能不能规模做）

风险最高              风险最高              收益决定
↓                     ↓                     ↓
若失败：概念不成立    若失败：退回展示方案    若失败：单体项目
```

**核心判断**：项目真正的风险不在技术实现，而在两个假设是否成立——
1. **互动假设**：观众行为能否稳定驱动宠物反馈，并产生可感知的娱乐价值
2. **接入假设**：能否通过官方授权渠道拿到直播互动事件

这两点任一不成立，商业化就无从谈起。因此路线按「先证伪、后放大」排列。

---

## 第一阶段：验证互动玩法

### 技术目标

| 编号 | 目标 | 说明 |
|------|------|------|
| T1-1 | 跑通「事件 → 规则 → 动作 → 播放」链路 | 不依赖任何真实平台 |
| T1-2 | 验证规则可配置 | 改配置即改行为，不改代码 |
| T1-3 | 验证多角色可扩展 | 新增角色仅需加目录 + config.json |
| T1-4 | 验证异常不中断 | 素材缺失降级 idle |
| T1-5 | 建立数据可观测性 | 每次互动可落库、可统计 |

### 关键技术决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 事件入口 | 事件模拟器（非按钮直连） | 提前引入网关层，避免后期返工 |
| 平台抽象 | 先定接口，后做实现 | 接口错了改实现，实现错了改全局 |
| 规则引擎 | 外部配置文件 | 让非开发人员也能调行为 |
| 展示方式 | 网页渲染 | 便于后续接 OBS |

### 风险

| 风险 | 等级 | 应对 |
|------|------|------|
| 互动体验平淡，观众无感 | **高** | 早期找真人做小范围测试，收集主观反馈 |
| 动作素材质量不足 | 中 | 验证阶段用占位素材，重点验证机制而非画面 |
| 过度设计，链路臃肿 | 中 | 严格 P0 清单，P1/P2 一律延后 |

### 验收标准

- [ ] 三类事件（gift / comment / follow）均可驱动宠物动作
- [ ] 动作播放完毕自动返回待机
- [ ] 修改 rules.json 可改变动作映射（无需改代码）
- [ ] 删除素材后系统降级 idle，不崩溃
- [ ] 互动记录正确落库并可查询
- [ ] **主观验证：至少 3 名非开发者观看演示后认为"有互动感"**

> 最后一条是本阶段最关键的验收项。技术跑通不等于玩法成立。

## 第二阶段：验证直播接入

### 技术目标

| 编号 | 目标 | 说明 |
|------|------|------|
| T2-1 | 展示端可被 OBS 采集 | 透明背景 + 尺寸适配 |
| T2-2 | 实时性达标 | 事件到画面延迟 < 500ms |
| T2-3 | 稳定性达标 | 连续 100 次触发无卡顿/泄漏 |
| T2-4 | 展示端与事件源解耦 | 支持分离部署 |

### 关键技术决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 通信方式 | WebSocket | 实时推送优于轮询 |
| 部署形态 | 前端独立可访问 | OBS 浏览器源可直接加载 |
| 画面比例 | 16:9 / 9:16 双适配 | 覆盖横屏与竖屏直播 |

### 风险

| 风险 | 等级 | 应对 |
|------|------|------|
| OBS 浏览器源兼容性问题 | 中 | 提前用 OBS 实测，而非仅浏览器验证 |
| 长时间运行内存泄漏 | 中 | 压测 + 内存监控 |
| 网络抖动导致状态不同步 | 中 | 状态快照 + 重连补偿 |

### 验收标准

- [ ] OBS 浏览器源可正常渲染，背景透明
- [ ] 事件到画面延迟 < 500ms
- [ ] 连续 100 次触发无卡顿，内存无持续增长
- [ ] 展示端可在独立机器运行
- [ ] 断开 WS 后自动重连并可恢复状态

## 第三阶段：商业化复制

### 技术目标

| 编号 | 目标 | 说明 |
|------|------|------|
| T3-1 | 平台适配器可插拔 | 新平台仅实现接口 |
| T3-2 | 多角色 / 多直播间隔离 | 单系统服务多场景 |
| T3-3 | 接入官方互动能力 | 授权合规前提下 |
| T3-4 | 数据支撑商业决策 | 互动数据可分析 |
| T3-5 | 部署可复制 | 标准化部署流程 |

### 关键技术决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 平台接入 | 仅走官方授权接口 | 合规底线，见红线 C5 |
| 数据存储 | SQLite → PostgreSQL | 单机验证够用，规模再升级 |
| 内容标识 | 明确标注 AI 生成 | 合规要求，见产品定位原则 |

### 风险

| 风险 | 等级 | 应对 |
|------|------|------|
| **官方 SDK 不可得 / 审核不通过** | **最高** | 设 Go/No-Go 闸门；备选退回展示型方案 |
| 平台政策变动 | **高** | 保持 Adapter 层隔离，快速切换平台 |
| AI 生成内容合规风险 | **高** | 全链路标注 AI 属性，规避误导 |
| 未经授权数据抓取冲动 | **高** | 红线明令禁止，不列入任何方案 |
| 成本失控（带宽/存储） | 中 | 素材压缩规范 + CDN 策略 |

### 验收标准

- [ ] 新增平台接入无需修改核心业务代码
- [ ] 多直播间并行运行互不干扰
- [ ] 真实直播间礼物事件可稳定驱动动作
- [ ] 断线重连成功率 > 95%
- [ ] 峰值 50 事件/秒系统稳定
- [ ] 合规审查通过，AI 内容属性标注完整

## 路线关键闸门

| 闸门 | 位置 | 决策内容 | 不通过的处理 |
|------|------|----------|--------------|
| **G1** | 第一阶段结束 | 互动玩法是否成立 | 重新设计互动机制，或终止项目 |
| **G2** | 第二阶段结束 | 展示形态是否可用 | 调整展示方案（如改为视频合成） |
| **G3** | 第三阶段结束 | 平台接入是否可行且合规 | 退回展示型方案，放弃实时接入 |

> **G3 是最高风险闸门**。官方接口的可得性不由技术决定，建议在第一阶段就并行启动 SDK 调研，不要等到第三阶段才发现走不通。
