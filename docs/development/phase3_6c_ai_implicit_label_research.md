## 一、GB 45438-2025 要求（4.1 调研结果）

### 1.1 字段名与结构（**国标原文**）

- **字段名/关键词须包含 `AIGC`**（GB 45438—2025 **附录 E a)**，**规范性**）
- **字段值为 JSON 字符串**（附录 E b) 逐字）：

```
{"AIGC":{"Label":"value1","ContentProducer":"value2","ProduceID":"value3",
"ReservedCode1":"value4","ContentPropagator":"value5","PropagateID":"value6","ReservedCode2":"value7"}}
```

| 键 | 含义 | 取值 |
|---|---|---|
| `Label` | 标识类型 | `1`=属于 / `2`=可能 / `3`=疑似 |
| `ContentProducer` | **生成合成服务提供者**名称或编码 | 字符串 |
| `ProduceID` | **内容制作编号** | 字符串 |
| `ReservedCode1` | 预留 1（安全防护） | 字符串 |
| `ContentPropagator` | **传播服务提供者** | 字符串 |
| `PropagateID` | **传播编号** | 字符串 |
| `ReservedCode2` | 预留 2 | 字符串 |

- **字符集**：值应主要由 **GB 18030—2022** 指定码位字符构成（除 `"` 与 `\` 外的单字节可打印字符，`\` 作转义）
- **首次写入规则**（附录 E 注 1）：生成者首次写入时，**传播要素 = 生成者要素、传播编号 = 制作编号**
- **唯一性**（6.1 c)）：内容文件中**应仅保留一份**文件元数据隐式标识
- **数字水印**：**准许**采用，但附录 A 注明确「**在本文件中不做要求**」（虚线框）

### 1.2 适用范围与义务主体

| 调研项 | 结论 |
|---|---|
| **模态** | **全模态**（文本 / 图片 / 音频 / 视频 / 虚拟场景）；隐式标识为**统一要求** |
| **主体** | 义务落在 **生成合成服务提供者**（首次写入）**与 内容传播服务提供者**（核验并**补写传播要素**）；用户须主动声明 |
| **文件格式** | 要求**不同**：字段语义统一，但**写入层级不同**（见第二节） |

### 1.3 生效时间与过渡期

## 二、文件格式差异（写入层级）

> 依据：TC260 于 **2025-08-28** 发布的 6 项《网络安全标准实践指南》（配套 GB 45438）。

| 格式 | 写入层级 / 方案 |
|---|---|
| **MP4 / MOV** | ⭐ **原生嵌入**：存储位置 **`moov.udta.meta`**；`meta/keys` 写 key = **`AIGC`**，`meta/ilst` 写 value（JSON） |
| **AVI** | 原生嵌入（基于 **RIFF** 规范） |
| **MKV / WebM** | 原生嵌入（基于 **Matroska** 规范，Tags/EBML） |
| **FLV** | 原生嵌入：**`script.onMetaData`** |
| **视频-其他格式** | **XMP 规范方案** |
| **JPEG / JPG** | 通用元数据方案（行业多以 **XMP**：APP1/APP13 或 uuid 承载） |
| **PNG** | 同上（**tEXt / iTXt / zTXt** 块或 XMP-iTXt） |
| **WAV / MP3 / OGG / FLAC / M4A** | 原生嵌入（各自原生结构）；其他走 **XMP** |

> **要点**：**mp4 vs jpg/png/wav 的差异在「写到文件哪一层」，不在「字段语义」** —— `AIGC` + `Label/ContentProducer/…` 的 JSON 语义全格式一致。

## 三、素材生成管线改造方案（4.3 方案对比）

| 方案 | 描述 | 代价 / 风险 | 官方契合度 |
|---|---|---|---|
| **A. 生成工具内置** | 由 AI 生成工具在生成时自动写入 | ⚠️ **依赖外部工具**，而各工具是否内置写入**未检索到公开证据**（Sora 用 **C2PA** 而非国标 `AIGC` 字段 ⇒ **不可依赖**） | ⭐ **制度本意**（义务主体 = 生成合成服务提供者；附录 E 注 1 的「首次写入」规则为生成端设计） |
| **B. 后处理脚本** | 生成后用 **ffmpeg 无损 remux** 补写 `AIGC` | 需开发脚本；⚠️ 依赖「交付链路中元数据未被剥离」；⚠️ **法律上不能替代生成者义务** | ✅ **官方对 mp4 的落地方式就是 ffmpeg**，工程路径最短、可批量、`-c copy` 无损秒级 |
| **C. 元数据文件（sidecar）** | 独立 JSON 与素材并列存放 | 国标与视频指南均强调**写入文件内部**（`moov.udta.meta` 等）；sidecar **易丢失、传播不随行** ⇒ 无法满足「文件元数据隐式标识」 | ⛔ **最弱**（仅在内部留档/审计台账等**非合规用途**中有意义） |

**官方 mp4 写法（可直接执行）**：

```bash
ffmpeg -i input.mp4 \
  -metadata AIGC='{"Label":"1","ContentProducer":"<生成者>","ProduceID":"<编号>","ReservedCode1":"","ContentPropagator":"<传播者>","PropagateID":"<编号>","ReservedCode2":""}' \
  -movflags use_metadata_tags \
  -c copy output.mp4
```

- `-c copy` = **不重编码**（仅重写容器 tag 表，无损、秒级）
- `-movflags use_metadata_tags` = **关键**：让 MP4 保留非标准自定义 key（否则被丢弃）
- 批量补写时应加 `-map_metadata 0` 以免覆盖既有元数据

**验证命令**：

```bash
ffprobe -v error -show_entries format_tags -of default=noprint_wrappers=1 f.mp4   # 看是否出现 AIGC
ffprobe -v quiet -print_format json -show_format f.mp4                            # JSON（便于 CI 断言）
exiftool -a -G1 -s f.mp4                                                          # 看 keys/ilst、XMP、JUMBF
```

| 校验工具 | 用途 | 备注 |
|---|---|---|
| `ffprobe` | 容器层是否存在 `AIGC` | 本仓库**已有先例调用**（`asset_duration.py`） |
| `exiftool` | MP4 keys/ilst、XMP、JUMBF | ⚠️ **本机不在 PATH** |
| `c2patool` | 读/验 C2PA 清单 | 仅当采用 C2PA 路线时相关 |

## 四、与现有架构的映射（4.4 调研结果）

| 调研项 | 结论（含仓库事实） |
|---|---|
| **素材入库是否应校验元数据** | ✅ **建议**（非本报告裁决）：`backend/scripts/init_assets.py` 是**天然落点**（已有 CLI 入口 + 已在用 ffprobe）。但⚠️ **写入/校验元数据属新增能力** —— `AssetManager` 是**唯一素材解析点**（冻结），且「元数据写入」在任何冻结文档中**均无归属** ⇒ **须经 CR** |
| **播放时前端是否需读取** | ⛔ **不需要，且禁止**：**UB-4**（前端只消费 `asset_url`）+ **FP-3**（禁前端判语义）⇒ 前端**不得**读元数据；浏览器 `<video>` 也不暴露容器 tag |
| **合规审计如何验证** | 建议在**入库/发布前**用 `ffprobe -show_entries format_tags` 做断言（可脚本化、可进 CI）；⚠️ 素材是**受 git 跟踪的二进制**（15 个 mp4）⇒ 「是否把元数据写回仓库素材」本身是一个**需 owner 裁决的独立问题**（涉仓库体积与可复现性） |

**既有可复用件**：`asset_duration.py` 的 ffprobe 封装（路径解析 / 超时 / 错误语义）可作为「读取侧」验校的**模式先例**；但**写入侧**无先例。

## 五、推荐方案（**仅排序 + 理由，不代裁**）

**排序：B（后处理脚本）＞ A（生成工具内置）＞ C（独立元数据文件）**

| 排序 | 方案 | 理由 |
|---|---|---|
| **1** | **B 后处理脚本** | ① 官方对 **mp4** 的落地方式**就是 ffmpeg**（有官方命令）⇒ 工程路径最短；② `-c copy` 无损、秒级、可批量 ⇒ 成本最低；③ 素材来自**外部工具**（是否内置写入不确定）⇒ 主动补写可**确定性闭合缺口**；④ 可接入入库校验断言。**反面**：依赖交付链路不剥离元数据，且**不能替代生成者义务** |
| **2** | **A 生成工具内置** | ① **制度本意**（义务主体 = 生成合成服务提供者）；② 附录 E 注 1 的「首次写入」规则为生成端设计；③ 可避免「事后补写是否算真实制作信息」的疑问。**反面**：本项目素材由**外部工具**生成，其是否内置写入**未检索到公开证据** ⇒ **不可依赖** |
| **3** | **C 独立元数据文件** | 国标与指南均要求**写入文件内部**；sidecar **易丢失、传播不随行** ⇒ 无法满足合规要求（仅内部台账有意义） |

> ⚠️ **未下最终结论**：取 B 还是 B+A 组合、以及 `ContentProducer` / `ProduceID` 的取值口径（是否需 27 位服务提供者编码），取决于本项目在链路中的**主体角色**与编解码资质，**建议结合第六节未确认项与法务确认后由 owner 裁决**。

## 六、关键风险与未确认项

### 6.1 风险

| 风险 | 说明 | 严重度 |
|---|---|---|
| **元数据可被剥离** | 平台转码/上传可能丢弃 `moov.udta.meta` 自定义 key ⇒ 补写**不等于**传播后仍带标识 | 🔴 |
| **不能替代生成者义务** | 义务主体是**生成合成服务提供者**；事后补写**不改变**法定责任分配 | 🔴 |
| **字段序列化口径不一** | 国标附录 E（**外层** `{"AIGC":{…}}`）与视频指南 MP4 实现（key=`AIGC` + value=**内层** `{…}`）**呈现不一致** | 🟠 |
| **素材为受 git 跟踪的二进制** | 15 个 mp4 在库内；写回元数据会改动受跟踪二进制（仓库体积 / 可复现性） | 🟠 |
| **写入侧无冻结归属** | 「元数据写入」在任何冻结文档中**无归属** ⇒ 直接实现会破边界 | 🟠 |
| **本机缺校验工具** | `exiftool` 不在 PATH（`ffprobe` 可用） | 🟡 |
| **有 C2PA 签名时写入会使其失效** | 若素材带 C2PA，任何写操作（含 remux）会破坏原签名 | 🟡 |

| # | 未确认项 |
|---|---|
